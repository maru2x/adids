# テスト方針

## 目的

このドキュメントは、`adids` で現在どういうテストを持っていて、何を守ろうとしているのかを初見の人や他のモデル向けにまとめたもの。

このプロジェクトのテストは、今のところ「実験でよく使う導線が壊れていないか」を素早く確認するための回帰テストを中心にしている。網羅的な品質保証というより、壊れやすい要所を少ないコストで守る方針。

## テスト戦略の全体像

現在のテストは大きく 3 層ある。

1. ドキュメント整合チェック
- `README.md`
- `AGENTS.md`
- `docs/`

の最低限の整合を守る。

2. CSV 加工ユーティリティのテスト
- `csv_daytime_override.py`
- `two_csv_combine.py`
- `log_to_csv_extractor.py`

の設定どおりの時刻移動と失敗系を守る。

3. 手動検証用スクリプト置き場
- `tests/manual/`

には、CI に入れていない検証スクリプトや補助ファイルを分離して置く。

## なぜこの方針か

`adids` は、次の 2 系統がつながって動く。

1. 前処理
- `src/util/FeatureExtract/Zeek/`
- `src/util/FeatureExtract/Legacy/`

2. 実行本体
- `src/main/`

実験で一番使うのは Zeek モードの

```text
pcap -> zeek json logs -> csv -> make run
```

という導線だが、現状の自動テストはその前段の CSV 加工ユーティリティと docs 整合の回帰を優先している。

逆に、今の CI は次までは守っていない。
- `pcap -> zeek log`
- `make run` のスモーク
- 実 `zeek` バイナリを使った統合確認
- 実 PCAP を使った通し試験
- 全 `MODEL_CODE` の動作保証
- 性能試験
- 長時間実行試験

## 現在のテストファイル

### `tests/unit/test_docs_consistency.py`

役割:
- ドキュメントの更新漏れを早い段階で止める

見ていること:
- 必須 docs が存在するか
- `README.md` が必須 docs を参照しているか
- `AGENTS.md` が必須 docs を参照しているか
- `README.md` と `AGENTS.md` が主要コマンドを共有しているか
- `AGENTS.md` に docs 整合ルールと Definition of Done があるか

狙い:
- コードだけ変わって docs が古いまま残るのを防ぐ
- 他モデルが repo を開いたときの初期理解を壊さない

### `tests/unit/test_csv_daytime_override.py`

役割:
- `DataModified` の時刻ずらしユーティリティの最低限の回帰を守る

見ていること:
- 入力ディレクトリ内の最初の `daytime` が `BASELINE` に揃うか
- 全行が同じ差分で平行移動されるか
- 入力 CSV を破壊せず、新しい leaf ディレクトリへ出力するか
- `daytime` 列欠落を説明付きで弾けるか

### `tests/unit/test_two_csv_combine.py`

役割:
- `DataModified` の CSV 結合ユーティリティの時系列結合を最低限守る

見ていること:
- 片側入力が先に尽きても未出力バッファを落とさず最後まで結合できるか
- `CHUNK_SIZE` ちょうどでファイル分割できるか
- ヘッダ不一致を説明付きで弾けるか
- `daytime` 不正値を弾けるか
- 空入力や不正 `CHUNK_SIZE` を弾けるか
- 既存ファイルのある `OUTPUT_DIR` を弾けるか

### `tests/unit/test_zeek_log_to_csv_extractor.py`

役割:
- Zeek の `log-to-csv` における `daytime` 生成と並び順の最低限の回帰を守る

見ていること:
- `conn.log` の入力順ではなく `ts + duration` ベースで昇順に並ぶか
- `duration = 0` を欠損扱いせず有効値として扱うか
- `duration` が空文字や非数値のときだけ `ts` ベースへフォールバックするか

### `tests/manual/`

役割:
- CI に載せていない検証スクリプトやローカル用の補助ファイルを分離して置く

注意:
- `make docs-check` / `make test` の対象ではない
- 自動テストは `tests/unit/` 直下の `test_*.py` に限定する

## どう実行するか

### 最低限

```bash
make docs-check
make test
```

### それぞれの意味

`make docs-check`
- docs 整合だけを見る
- 仕様変更後の docs 更新漏れ確認に向く

`make test`
- `compileall` による構文チェック
- `tests/unit/` の自動テスト

## CI の位置づけ

GitHub Actions は `make test` を実行する。
docs 整合のチェックは `make docs-check` で別に確認する。

ただし CI の意味は「現行の主経路に対する最低限の防波堤」であって、「実験品質を完全保証するもの」ではない。

## 新しいテストを足すときの方針

新規テストは、次の順で考えるのがよい。

1. まず再現したい破壊パターンを 1 つに絞る
- 例: `DATASETS_DIR_PATH` にディレクトリが混ざる
- 例: `TARGET_LOGS` の単一指定で出力先が崩れる

2. 最小 fixture で再現する
- 実 PCAP や巨大 CSV を使う前に、数行の人工データで再現する

3. どの層の責務かを明確にする
- docs の問題なら `tests/unit/test_docs_consistency.py`
- CSV 加工なら `tests/unit/test_csv_daytime_override.py` や `tests/unit/test_two_csv_combine.py`
- 手元の一時検証だけなら `tests/manual/`

4. 既知の未解決問題を無理に green 化しない
- たとえば `dy + ENSEMBLE_METHOD_CODE=0` は、今は仕様自体に問題がある
- この手の問題は、まず実装修正の方針を固めてから回帰テストに落とす

## 現時点での限界

今のテストでは次はまだ守れていない。

- `pcap -> zeek log` の自動テスト
- 実 `zeek` を使った `pcap -> zeek log -> csv` の自動統合テスト
- 本体 `make run` の自動スモーク
- 実 `zeek` を使った統合試験
- 実 PCAP から本体までの通し試験
- Legacy モードの自動テスト
- `MODEL_CODE` 全種の動作確認
- `dy` の予測集約ロジックの正しさ
- 実験結果の品質評価
- 大量データや長時間実行の安定性

つまり、`make test` が通っても「実験結果が妥当」とまでは言えない。保証できるのは、主経路の基本的な構造が壊れていないことまで。

## 次に強化するなら

優先度としては次の順が自然。

1. `pcap -> zeek log` と `zeek log -> csv` の自動テスト追加
2. 実 `zeek` を使う `pcap -> zeek log` 側の自動テスト追加
3. 本体 `make run` の最小スモーク追加
4. `dy` の既知バグ修正と回帰テスト化
5. Legacy 導線のテスト追加
