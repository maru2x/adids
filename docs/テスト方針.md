## 概要

本プロジェクトのテストでは、主に以下2系統の処理の品質を検証する。

- 特徴量抽出処理
  - `pcap -> zeek log -> csv` が期待通りに動くこと
  - CSV の列、`daytime`、ラベル、並び順、除外条件が崩れないこと
  - CSV 加工ユーティリティが入力を壊さず、期待する変換を行うこと
- 実行本体
  - `make run` が期待通りに動くこと

## `tests/` のディレクトリ構成と役割

現在の構成は次の通り。

```text
tests/
├─ unit/
│  ├─ data_modified/
│  └─ feature_extract/
├─ e2e/
│  ├─ feature_extract/
│  └─ runtime/
├─ fixtures/
│  ├─ pcap/
│  ├─ expected_csv/
│  └─ zeek_logs/
└─ manual/
```

### `tests/unit/`

1 つのスクリプトやロジック単位を直接検証するテストを置く。
小さい仕様を固定することで、失敗時の切り分けをしやすくする。いわゆる単体テスト。

### `tests/e2e/`

実際に使う導線を最初から最後まで通すテストを置く。
実利用に近い形で壊れていないことを確認する。

### `tests/fixtures/`

テストに使用するデータ。

補足:

- stable な `golden` 比較用の tiny UDP fixture と、DNS / HTTPS のような protocol-specific fixture は分けて管理する
- bulk 用には、複数 `pcap` を同一 batch にまとめる専用 dataset を別に持つ
- protocol-specific fixture は `tests/fixtures/pcap/protocol_traffic/` に置き、将来 `dns.log` や `ssl.log` を扱うテストの土台にする

### `tests/manual/`

CI に載せないローカル確認用のスクリプトや補助ファイルを置く。
品質保証の基準にはしないが、一時検証を自動テストから分離するための置き場として扱う。

現在の unit テストで主に固定している内容は次の通り。

- `pcap_to_log_extractor.py`
  - 入力 PCAP の再帰収集
  - 相対パス解決
  - 最小 `ts` 読み取り
  - 重複ディレクトリ名の suffix 付与
  - `zeek` 実行失敗時の例外伝播
- `log_to_csv_extractor.py`
  - `daytime` の flow end time 基準ソート
  - `duration` 欠損時の start time フォールバック
  - `duration = 0` の扱い
  - `TARGET_LOGS` の正規化
  - ログディレクトリ探索
  - JSON 読み込み失敗時の異常系
  - ラベル付けと除外条件
  - list / dict の CSV 文字列化
- `two_csv_combine.py`
  - 時系列 merge
  - chunk 分割
  - header mismatch と不正入力の扱い
- `csv_daytime_override.py`
  - baseline への平行移動
  - `daytime` 欠損時の失敗

## テストの実行方法

テスト用の `make` コマンドとして、以下3つを用意している。

- `make unit-test`
  - `tests/unit`ディレクトリに記述したunitテストをすべて実行する
- `make test-e2e`
  - `tests/e2e`ディレクトリに記述したe2eテストをすべて実行する
- `make test-all`
  - unitテスト、e2eテストをすべて実行する

Github Actions 上の CI では、現在次の 3 job を push / pull_request ごとに実行する。

- `unit`
  - `make unit-test`
- `e2e_feature_extract`
  - `tests/e2e/feature_extract`
  - 公式 `zeek/zeek:8.0.5` の Debian ベース image を使う
- `e2e_runtime`
  - `tests/e2e/runtime`

現在の e2e テストで主に固定している内容は次の通り。

- `pcap -> zeek log -> csv`
  - `pcap_to_log_extractor.main()` の timestamp dir レイアウト
  - `log_to_csv_extractor.main()` の leaf CSV dir レイアウト
  - `daytime` が flow end time 由来で生成されること
  - tiny / scenario / bulk の expected CSV fixture との golden 比較
  - bulk では、専用の複数 `pcap` dataset を使った batch 単位の expected CSV 比較
  - benign / malicious / exception fixture の主要挙動
  - 複数行 fixture と複数 pcap batch の確認
  - protocol-specific fixture から `dns.csv` / `ssl.csv` を生成し、expected CSV と比較できること
- runtime
  - `src/main/` を使った最小 CSV の smoke 実行
  - 出力ファイル生成と `res_eval.csv` の基本 schema 確認


## 補足

現時点では、次はまだ自動では守れていない。

- `make run` のより厳密な期待値テスト
- Legacy モードの自動テスト
- `MODEL_CODE` 全種の動作確認
- `dy` の予測集約ロジック
- 実験結果そのものの品質評価
- 大量データ・長時間実行の安定性

したがって、`make unit-test` や `make test-all` が通っても「実験結果が妥当」とまでは言えない。
保証できるのは、現時点で自動化した前処理ロジックとその周辺契約が大きく壊れていないことまでである。
