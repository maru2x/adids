# テスト方針

## テストの役割

`adids` におけるテストの役割は、主に次の 3 つである。

1. 実験で使う導線が壊れていないことを確認する
2. 入力データや設定の契約が崩れていないことを確認する
3. 仕様変更時に、既存の重要な挙動が意図せず変わっていないことを確認する

このプロジェクトでは、特に Zeek モードの

```text
pcap -> zeek json logs -> csv
```

の導線が重要である。

理由:
- `make run` は CSV を入力として使う
- そのため、前処理が壊れると後段の評価結果も信用できなくなる
- 実際に問題になりやすいのも、学習器そのものより前処理と入出力契約である

## 概要

現在のテストは、次の 3 つを対象にしている。

### 1. 特徴量抽出

対象:
- `src/util/FeatureExtract/Zeek/`
- `src/util/FeatureExtract/Legacy/`
- `src/util/DataModified/`

ここでは次を守る。
- `pcap -> zeek log -> csv` が期待通りに動くこと
- CSV の列、`daytime`、ラベル、並び順、除外条件が崩れないこと
- CSV 加工ユーティリティが入力を壊さず、期待する変換を行うこと

### 2. 実行本体

対象:
- `src/main/run.py`
- `src/main/session_controller.py`
- `src/main/session_definer.py`
- `src/main/drift_detection.py`
- `src/main/trainer.py`
- `src/main/evaluator.py`
- `src/main/model_factory.py`

ここでは将来的に次を守る。
- CSV を入力して最後まで落ちずに実行できること
- 学習、推論、評価、概念ドリフト検出、再学習の導線が破綻していないこと
- `exp/` 配下に期待する出力が作られること

現時点では、この層の自動テストはまだ十分に整備されていない。

### 3. 契約と docs 整合

対象:
- `README.md`
- `AGENTS.md`
- `docs/`
- 設定ファイル
- CSV スキーマ
- ディレクトリ構造

ここでは次を守る。
- 実装と docs が矛盾しないこと
- テスト導線、実行導線、CSV 契約が明示されていること
- repo を開いた人が誤解なく利用できること

## 使用しているソフトウェア

現在の自動テストは `pytest` を使っている。

補足:
- `make test` は `compileall` による構文チェックも併用する
- Zeek を実際に使う E2E は `zeek` コマンドが入っている環境でのみ有効
- GitHub Actions では `make docs-check` と `make test` を実行する

## 実行方法

### docs 整合だけ確認する

```bash
make docs-check
```

用途:
- docs 更新漏れの確認
- `README.md` / `AGENTS.md` / `docs/` の最低限の整合確認

### 既定の自動テストを実行する

```bash
make test
```

内容:
- `src/` の `compileall`
- `pytest tests/unit`

### Zeek を使う通しテストを実行する

```bash
make test-e2e
```

内容:
- `pytest tests/e2e -m e2e`

注意:
- `zeek` コマンドがない環境では skip になる
- CI では回していない
- runtime E2E もここに含める

## `tests/` のディレクトリ構成と役割

現在の構成は次の通り。

```text
tests/
├─ unit/
│  ├─ contracts/
│  ├─ data_modified/
│  └─ feature_extract/
├─ e2e/
│  ├─ feature_extract/
│  └─ runtime/
├─ fixtures/
│  ├─ pcap/
│  ├─ expected_csv/
│  └─ zeek_logs/
└─ manual/
```

### `tests/unit/`

1 つのスクリプトやロジック単位を直接検証するテストを置く。

役割:
- 小さい仕様を固定する
- 失敗時の切り分けをしやすくする

#### `tests/unit/contracts/`

役割:
- docs 整合
- テスト導線
- 最低限の repo 契約

#### `tests/unit/data_modified/`

役割:
- CSV 加工ユーティリティの回帰確認

#### `tests/unit/feature_extract/`

役割:
- 特徴量抽出ロジックの回帰確認
- Zeek 前処理の個別仕様確認
- `pcap_to_log_extractor.py` の補助ロジック確認

### `tests/e2e/`

実際に使う導線を最初から最後まで通すテストを置く。

役割:
- 実利用に近い形で壊れていないことを確認する

#### `tests/e2e/feature_extract/`

役割:
- `pcap -> zeek log -> csv` の通し確認

#### `tests/e2e/runtime/`

役割:
- `src/main/` の最小 runtime 導線確認

### `tests/fixtures/`

固定入力と期待値を置く。

役割:
- `unit` と `e2e` の再現条件を固定する
- 実験データとテストデータを分離する

方針:
- fixture はできるだけ小さくする
- 1 fixture 1 論点に寄せる
- 実データと混ぜない

#### `tests/fixtures/pcap/`

役割:
- Zeek E2E 用の極小 PCAP

#### `tests/fixtures/expected_csv/`

役割:
- E2E の期待結果 CSV

#### `tests/fixtures/zeek_logs/`

役割:
- `log -> csv` 系テストで使う固定ログ

### `tests/manual/`

CI に載せないローカル確認用のスクリプトや補助ファイルを置く。

注意:
- 品質保証の基準にはしない
- 一時検証を自動テストから分離するための置き場として扱う

## 各テストの詳細

### `tests/unit/contracts/test_docs_consistency.py`

目的:
- docs 更新漏れを早い段階で止める

見ていること:
- 必須 docs が存在するか
- `README.md` と `AGENTS.md` が主要コマンドを共有しているか
- `make docs-check` の導線があるか
- `tests/unit/` が責務別に分かれているか
- `AGENTS.md` が既存の自動テストファイルを列挙しているか

### `tests/unit/data_modified/test_csv_daytime_override.py`

目的:
- `csv_daytime_override.py` の最低限の回帰を守る

見ていること:
- `BASELINE` への時刻平行移動
- 入力 CSV を壊さないこと
- `daytime` 欠落時に説明付きで失敗すること

### `tests/unit/data_modified/test_two_csv_combine.py`

目的:
- `two_csv_combine.py` の時系列結合処理を守る

見ていること:
- 時系列順の結合
- chunk 単位の分割
- ヘッダ不一致の検出
- 不正 `daytime` の検出
- 空入力や不正 `CHUNK_SIZE` の検出
- 出力先ディレクトリの安全性

### `tests/unit/feature_extract/test_zeek_log_to_csv_extractor.py`

目的:
- `log_to_csv_extractor.py` の `daytime` 生成と並び順の仕様を守る

見ていること:
- `ts + duration` ベースで並び替えること
- `duration=0` を欠損扱いしないこと
- `duration` が欠落・空文字・非数値のときだけ `ts` ベースへフォールバックすること

### `tests/unit/feature_extract/test_pcap_to_log_extractor.py`

目的:
- `pcap_to_log_extractor.py` の補助ロジックと異常系を守る

見ていること:
- `.pcap` / `.pcapng` の再帰収集
- 相対パス解決
- 最小 `ts` 読み取り
- 既存ディレクトリへの連番 suffix
- `zeek` 実行失敗時のエラー伝播

### `tests/e2e/feature_extract/test_zeek_pcap_to_csv.py`

目的:
- Zeek を使った実際の前処理導線が壊れていないことを確認する

見ていること:
- 固定 `pcap` fixture から `conn.log` が生成されること
- `conn.log` から CSV が生成されること
- 最終 CSV の主要列が期待値と一致すること
- `daytime` が昇順であること

注意:
- `zeek` が入っていない環境では skip する
- 現在は `roundtrip`, `interleaved`, `one-way` の 3 fixture を持つ

### `tests/e2e/runtime/test_run_smoke.py`

目的:
- `src/main/` の最小 runtime 導線が落ちずに動くことを確認する

見ていること:
- 最小 split CSV を入力して出力ディレクトリが作られること
- `settings_log.json` と `res_eval.csv` が生成されること
- 最低限の評価結果サマリが期待する件数になること

## 補足

現時点では、次はまだ自動では守れていない。

- 実 `zeek` を使う E2E の CI 常設
- `make run` のより厳密な期待値テスト
- Legacy モードの自動テスト
- `MODEL_CODE` 全種の動作確認
- `dy` の予測集約ロジック
- 実験結果そのものの品質評価
- 大量データ・長時間実行の安定性

したがって、`make test` が通っても「実験結果が妥当」とまでは言えない。
保証できるのは、現時点で自動化した前処理ロジックとその周辺契約が大きく壊れていないことまでである。
