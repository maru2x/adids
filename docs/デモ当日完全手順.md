# デモ当日完全手順

## 目的

この手順は、何も覚えていない状態からでも次の 2 本を順番に見せられるようにするための runbook である。

1. AWS 側で収集した Cowrie 攻撃通信を Kibana で見る
2. ローカル fake IoT SSH サービスに対する疑似攻撃を `make run-live` が console alert で検知する

## 使う terminal

- Terminal A: local ELK / Kibana 周辺
- Terminal B: local live IDS runtime
- Terminal C: local demo compose 状態確認
- Attack PC: 同一 LAN 上の別マシン

## 0. 開始前にやること

repo root にいることを確認する。

```bash
pwd
```

`.venv` があるか確認する。

```bash
ls .venv/bin/python
```

無ければ:

```bash
make bootstrap
```

## 1. Demo1 の local ELK を上げる

Terminal A:

```bash
make elk-up-cowrie-live
make kibana-import-cowrie-live-dashboard
make elk-ps
```

期待すること:

- `es01`
- `kibana`
- `filebeat-cowrie01`
- `filebeat-cowrie-live01`

が `Up` になっている。

Kibana は `http://localhost:5601` を開く。

開く dashboard:

- `Cowrie Live Attack Monitoring`

## 2. Demo2 の local live IDS を初期化する

Terminal C:

```bash
make demo-live-down
make demo-live-reset
make prepare-live-demo-model
make demo-live-up
make demo-live-ps
```

期待すること:

- `fake_iot_device` が `0.0.0.0:2223->2222/tcp`
- `zeek-local-live` が `Up`

補足:

- `zeek-local-live` は host 側 interface を自動検出する
- 自動検出が怪しいときだけ `ZEEK_LIVE_INTERFACE=<LAN_INTERFACE> make demo-live-up` を使う

## 3. local live IDS runtime を起動する

Terminal B:

```bash
make run-live
```

最初にこういう行が出ることを確認する。

```text
[run-live] 開始: 入力=.../data/logs/zeek/live/local_iot/current / 出力=.../data/csv/live/local_iot_demo / threshold=0.5 / ports=[2223] / protos=['tcp']
```

この terminal はそのまま開いたままにする。

## 4. Attack PC から疑似攻撃を打つ

Attack PC で、手元 PC の LAN IP を指定して Hydra を実行する。

```bash
hydra -l iot -P passwords.txt ssh://<LOCAL_PC_LAN_IP>:2223 -t 4 -f
```

最小の `passwords.txt` 例:

```text
admin
password
raspberry
letmein
```

## 5. 期待する見え方

Kibana:

- `Cowrie Live Attack Monitoring` に AWS 側の flow が出ている

Terminal B:

```text
[ALERT] event_time=... src_ip=... dst_ip=... dst_port=2223 proto=tcp conn_state=... score=... label_key=... source_type=local_iot_demo
```

## 6. 当日の説明順

1. Kibana の `Cowrie Live Attack Monitoring` を開く
2. AWS 側で実攻撃の flow が集まっていることを見せる
3. local 側で `make run-live` が待機していることを見せる
4. Attack PC から Hydra を打つ
5. Terminal B に alert が出ることを見せる

## 7. 10 秒待っても alert が出ないとき

Terminal C:

```bash
make demo-live-ps
```

`zeek-local-live` が `Up` か確認する。

`conn.log` に `2223` があるか確認する。

```bash
rg '"id.resp_p":2223' data/logs/zeek/live/local_iot/current/conn.log
```

分岐:

- `2223` が無い
  - capture 側の問題
  - `docker compose -p adids-demo -f docker-compose.demo.yml logs --tail=20 zeek-local-live` を見る
- `2223` は有るが alert が無い
  - state が濁っている可能性が高い
  - 次を実行してやり直す

```bash
make demo-live-down
make demo-live-reset
make demo-live-up
```

その後、Terminal B で `make run-live` を再起動する。

## 8. 緊急 fallback

外部マシンや Hydra が使えないときは、Terminal C で次を打つ。

```bash
make demo-live-inject-alert
```

これは synthetic な `2223/tcp` 行を `conn.log` に追加して alert 導線だけを見せる emergency fallback である。

注意:

- この fallback は `zeek-local-live` を停止してから行を追加する
- fallback 後に capture を再開したいときは `make demo-live-up` を再実行する

## 9. 終了時

Terminal B で `Ctrl-C`。

Terminal A / C:

```bash
make demo-live-down
make elk-down
```
