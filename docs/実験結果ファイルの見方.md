# 実験結果ファイルの見方

## 概要

`make run` を実行すると、結果は `USER_DIR/exp/` 配下に出る。

出力ディレクトリ名の形式は次。

```text
<INIT_TIME>_<dataset_dir_name>_<RETRAINING_MODE>_<MODEL_CODE>
```

例:

```text
exp/20260322101009_2201AusEast_dy_0
```

ここで:
- `INIT_TIME`: 実行開始時刻
- `dataset_dir_name`: `DATASETS_DIR_PATH` の basename
- `RETRAINING_MODE`: `nt`, `st`, `dy`
- `MODEL_CODE`: `src/main/settings.json` の `MODEL_CODE`

## 1. 常に出るファイル

### `settings_log.json`

実行時に使った設定のスナップショット。

元の `settings.json` に加えて、`Log` に次が追記される。

- `INIT_TIME`
  - 実行開始時刻
- `SESSION_END_DAYTIME`
  - 実行終了時刻
- `ELAPSED_TIME`
  - 実行時間秒数

使いどころ:
- 実験条件の再現
- `exp/` ディレクトリ名と実際の設定値の対応確認

### `res_eval.csv`

評価結果の CSV。

ヘッダは次。

- `daytime`
- `label_key`
- `TP`
- `FN`
- `FP`
- `TN`
- `flow_num`
- `TP_rate`
- `FN_rate`
- `FP_rate`
- `TN_rate`
- `accuracy`
- `precision`
- `f1_score`
- `loss`
- `benign_rate`
- `nmr_fn_rate`
- `nmr_benign_rate`

#### `label_key`

意味:
- `default`
  - legacy モード、またはモデル分割がない場合
- `SF` など
  - `LABEL_FEATURES` から作られたキー
- `mixed:n`
  - 1つの評価区間に複数の `label_key` が混ざった場合
- `none`
  - 予測キーがない場合

#### `nmr_fn_rate` / `nmr_benign_rate`

本体の最終処理で追加される正規化列。

- `nmr_fn_rate`
  - 各評価行の `flow_num` を全体比率にしてから min-max 正規化した値
- `nmr_benign_rate`
  - `benign_rate` を min-max 正規化した値

注意:
- 短いデータで `EVALUATE_UNIT_INTERVAL` が長すぎると、`res_eval.csv` はヘッダだけで終わることがある

## 2. 再学習したときだけ出るファイル

### 非 zeek モード

出力例:

- `res_train_m0.csv`
- `res_train_m1.csv`

各行の列:
- `daytime`
- `accuracy`
- `loss`
- `training_time`
- `benign_count`
- `malicious_count`
- `flow_num`

意味:
- どの時刻に再学習したか
- そのときの学習結果
- 学習データの正常 / 攻撃件数

### zeek モード

出力例:

- `res_train_SF_m0.csv`
- `res_train_SF_m1.csv`
- `res_train_S0_m0.csv`

`SF`, `S0` の部分は `label_key` をファイル名向けに安全化したもの。

## 3. 重みファイル

### ルート直下の重みディレクトリ

出力例:

- `m0_weights/`
- `m1_weights/`

この中には、再学習時刻を名前にした pickle が入る。

例:

```text
m0_weights/2024-01-01T00:30:00.pickle
```

### zeek モードのキー別重み

zeek モードでは、キーごとに `keys/` 配下へ出る。

例:

```text
keys/
  SF/
    m0_weights/
    m1_weights/
  S0/
    m0_weights/
    m1_weights/
```

注意:
- キー名はそのままではなく、ファイル名に使えない文字を `_` に変換した安全名になる
- `m1_weights/` などのディレクトリは先に作られることがあるので、「ディレクトリがある = 学習済み」とは限らない
- 実際に中に pickle があるかを見る方が確実

## 4. `RETRAINING_MODE` ごとの見え方

### `nt`

- `settings_log.json` は出る
- `res_eval.csv` は出る
- `res_train_*.csv` は通常出ない
- 重み pickle も通常は増えない

### `st`

- 一定間隔で `res_train_*.csv` が増える
- 対応する重み pickle が出る

### `dy`

- ドリフト検知が起きたときだけ `res_train_*.csv` が増える
- 窓ごとに `m0`, `m1` などが分かれる
- zeek モードならキーごとにも分かれる

## 5. まず何を見ればいいか

### 実験が正常終了したか

1. `settings_log.json` があるか
2. `res_eval.csv` があるか
3. `res_eval.csv` がヘッダだけで終わっていないか

### 再学習が本当に起きたか

1. `res_train_*.csv` があるか
2. `m*_weights/*.pickle` があるか
3. zeek モードなら `keys/` 配下も見る

### 条件を再現したいか

- まず `settings_log.json` を見る
- 次に `DATASETS_DIR_PATH` と `RETRAINING_MODE` を確認する

## 6. よくある見間違い

- `m1_weights/` があるので学習したと思い込む
  - ディレクトリだけ先に作られている場合がある
- `res_eval.csv` があるので評価できたと思い込む
  - ヘッダだけで中身がないことがある
- zeek モードなのにルート直下のファイルだけ見て終わる
  - 実際の重みは `keys/<label_key>/` に出ているかもしれない
