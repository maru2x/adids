# テスト方針

## 目的

このドキュメントは、`adids` で現在どういうテストを持っていて、何を守ろうとしているのかを初見の人や他のモデル向けにまとめたもの。

このプロジェクトのテストは、今のところ「実験でよく使う導線が壊れていないか」を素早く確認するための回帰テストを中心にしている。網羅的な品質保証というより、壊れやすい要所を少ないコストで守る方針。

## テスト戦略の全体像

現在のテストは大きく 3 層ある。

1. ドキュメント整合チェック
- `README.md`
- `AGENTS.md`
- `src/docs/`

の最低限の整合を守る。

2. 前処理のテスト
- `pcap -> zeek log`
- `zeek log -> csv`

の入出力構造と失敗系を守る。

3. 本体のスモークテスト
- `make run` 相当の最短経路が最後まで走るか
- `nt` / `st` / `dy` の主要モードが最低限壊れていないか

を守る。

## なぜこの方針か

`adids` は、次の 2 系統がつながって動く。

1. 前処理
- `src/util/FeatureExtract/Zeek/`
- `src/util/FeatureExtract/Legacy/`

2. 実行本体
- `src/main/`

実験で一番使うのは Zeek モードの

```text
pcap -> zeek json logs -> csv -> make run
```

という導線なので、まずはここが壊れないことを優先している。

逆に、今の CI は次までは守っていない。
- 実 `zeek` バイナリを使った統合確認
- 実 PCAP を使った通し試験
- 全 `MODEL_CODE` の動作保証
- 性能試験
- 長時間実行試験

## 現在のテストファイル

### `tests/test_docs_consistency.py`

役割:
- ドキュメントの更新漏れを早い段階で止める

見ていること:
- 必須 docs が存在するか
- `README.md` が必須 docs を参照しているか
- `AGENTS.md` が必須 docs を参照しているか
- `README.md` と `AGENTS.md` が主要コマンドを共有しているか
- `AGENTS.md` に docs 整合ルールと Definition of Done があるか

狙い:
- コードだけ変わって docs が古いまま残るのを防ぐ
- 他モデルが repo を開いたときの初期理解を壊さない

### `tests/test_zeek_extractors.py`

役割:
- Zeek 前処理の回帰を守る

見ていること:
- `pcap-to-log` が `<output_root>/<input_dir_name>/<timestamp>/` 形式の出力を作るか
- Zeek 実行失敗時に `.tmp_*` が残らないか
- 拡張子なし PCAP の再帰リネーム補助が `--dry-run` と衝突検知を含めて動くか
- `log-to-csv` が `TARGET_LOGS` ごとにサブディレクトリを切るか
- `EXCEPTION` を含むレコードを CSV から落とせるか
- 不正 JSON を説明付きで弾けるか
- 単一 `TARGET_LOGS` でも `conn/` のようなログ名ディレクトリを作るか

注意:
- `zeek` 呼び出し自体は mock している
- つまり「Zeek コマンドが本当にその環境で動くか」は見ていない

### `tests/test_main_pipeline.py`

役割:
- 本体の最短導線を守る

見ていること:
- split スキーマの CSV があれば `make run` 相当が最後まで走るか
- `RETRAINING_MODE=nt` が動くか
- `RETRAINING_MODE=st` が動き、キー別の学習結果ファイルが出るか
- `RETRAINING_MODE=dy` が最低限最後まで走るか
- `DATASETS_DIR_PATH` が不正なときに失敗するか
- 必須列欠落や不正値を弾けるか

注意:
- ここでの `dy` は smoke test であって、予測品質まで保証していない
- 既知の問題である `ENSEMBLE_METHOD_CODE=0` の設計不備は、まだ修正も保証もしていない

## どう実行するか

### 最低限

```bash
make docs-check
make test
```

### それぞれの意味

`make docs-check`
- docs 整合だけを見る
- 仕様変更後の docs 更新漏れ確認に向く

`make test`
- `compileall` による構文チェック
- `tests/` の全テスト

## CI の位置づけ

GitHub Actions は `make test` を実行する。
そのため、`make test` が通る状態を維持すれば、基本的には CI も通る。

ただし CI の意味は「現行の主経路に対する最低限の防波堤」であって、「実験品質を完全保証するもの」ではない。

## 新しいテストを足すときの方針

新規テストは、次の順で考えるのがよい。

1. まず再現したい破壊パターンを 1 つに絞る
- 例: `DATASETS_DIR_PATH` にディレクトリが混ざる
- 例: `TARGET_LOGS` の単一指定で出力先が崩れる

2. 最小 fixture で再現する
- 実 PCAP や巨大 CSV を使う前に、数行の人工データで再現する

3. どの層の責務かを明確にする
- docs の問題なら `test_docs_consistency.py`
- 前処理なら `test_zeek_extractors.py`
- 本体なら `test_main_pipeline.py`

4. 既知の未解決問題を無理に green 化しない
- たとえば `dy + ENSEMBLE_METHOD_CODE=0` は、今は仕様自体に問題がある
- この手の問題は、まず実装修正の方針を固めてから回帰テストに落とす

## 現時点での限界

今のテストでは次はまだ守れていない。

- 実 `zeek` を使った統合試験
- 実 PCAP から本体までの通し試験
- Legacy モードの自動テスト
- `MODEL_CODE` 全種の動作確認
- `dy` の予測集約ロジックの正しさ
- 実験結果の品質評価
- 大量データや長時間実行の安定性

つまり、`make test` が通っても「実験結果が妥当」とまでは言えない。保証できるのは、主経路の基本的な構造が壊れていないことまで。

## 次に強化するなら

優先度としては次の順が自然。

1. `dy` の既知バグ修正と回帰テスト化
2. `DATASETS_DIR_PATH` の説明付きエラー化
3. 実 `zeek` を使う任意の統合テスト追加
4. Legacy 導線のテスト追加
5. `MODEL_CODE` ごとのサポート状況をテストに反映
